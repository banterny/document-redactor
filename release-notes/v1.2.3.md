# document-redactor v1.2.3

_Released 2026-07-29_

**Supersedes v1.2.2, which was incomplete.** If you are on v1.2.2 or earlier,
update. Detection results are unchanged.

## What's fixed

v1.2.2 fixed a defect where thirteen detection rules could freeze the browser
on ordinary document shapes — long runs of spaces, digits or hyphens, of the
kind produced by column-aligned tables and padded forms. That fix was verified
on Safari and on a current version of Chrome, and it was **incomplete for two
of the rules**.

Those two — the Korean phone-number label rule and the UK inquest-context rule
— depended on an optimisation that only newer versions of Chrome's JavaScript
engine perform. Measured on one machine, same input, same rule:

| engine | `ko-phone-context` | `uk-inquest-context` |
|---|---:|---:|
| V8 12.4 (≈ Chrome 124) | 93.8ms | 133.7ms |
| V8 13.6 (≈ Chrome 136) | 0.00ms | 0.00ms |

So on a browser roughly a year behind, both rules were still slow enough to
breach the tool's own 50ms budget, while appearing completely fixed on a
current one. **This affected older Chrome and Edge, not only Safari** — which
the v1.2.2 notes did not say, because it was not then known.

Both rules are now restructured so the cost does not depend on the engine
version: 0.10ms and 0.09ms on the older engine. This is a **structural** fix,
not a bound — the patterns accept exactly the same text as before, verified
across 74,604 label, separator, padding and value combinations with zero
differences, so nothing that was detected before is missed now.

## How this got caught

Continuous integration had never actually run on this repository. Enabling it
surfaced both rules on the first run, because the CI machine happened to be a
version behind the development machine.

Two things changed so that cannot recur quietly:

- The test gate is now **pinned to the older engine on purpose**. A redaction
  tool that runs in the browser should be measured against the oldest engine
  its users plausibly have, not the newest.
- The release build now runs the ReDoS gate. It previously did not — the
  release suite skipped that check entirely, which is how v1.2.2 shipped past
  it.

## Verify your download

Save both files to the same directory and run:

```bash
sha256sum -c document-redactor.html.sha256
# expected output:
#   document-redactor.html: OK
```

This build is byte-for-byte reproducible: clone the repository at tag `v1.2.3`
and run `bun run build`, and you will get exactly the published file. Verified
across Linux/x64 and macOS/arm64.

## Known limitations

- This is still a deterministic local pre-upload filter, not a legal judgment
  engine.
- The tool does not decide whether a legal reference is sensitive in your
  specific matter; review the candidate list before applying redaction.
- DOCX output is verified after rewrite, but unsupported package structures may
  still need manual handling.
- Two rules carry documented, test-pinned detection limits at extreme input
  sizes: the UK legal-label scanner stops bridging a label to its value beyond
  roughly 100–165 consecutive whitespace characters, and the Korean corporate
  suffix rule misses a company-name token longer than 256 characters that sits
  immediately after `&`, `.` or `-`. Neither shape occurs in real documents.
